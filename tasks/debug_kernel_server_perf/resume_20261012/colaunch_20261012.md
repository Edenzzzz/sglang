# A-fix: FA2 out of the co-compiled fused kernel (PDL co-launch)

## Why

On a decode-shaped FA2 row (one 8-token request, kv 4096) the fused kernel took 345 us per call
against 15 us for `BatchAttention` (nsys), both exact against the fp32 causal reference. The fused
kernel compiles at 168 registers with a 4200-byte stack (`BatchAttention`: 255 / 80-104 B), because
the FA2 body is co-compiled with, and capped by, the 384-thread FA3 role. Scheduling ablations
(backfill, budget split, SM split, tail dispatch) move it by <20%; making one FA2 item 4x longer
makes the call 3.5x longer. See [the A/B evidence](postfix_realistic_ab_20261012.md).

## Change (`colaunch_persistent_fa3_fused.patch`, flashinfer `port07/.../persistent_fa3_fused.cuh`)

`FLASHINFER_FUSED_COLAUNCH=1`:
- the FA3 grid launches alone on exactly `sm_split` CTAs with FA3-only shared memory, no backfill;
- `FA2ExecutorKernel` -- the same three FA2 runners, the same four-task plan and the same
  atomic-cursor queue, at native `__launch_bounds__(128, 2)` -- is launched as its programmatic
  dependent (`cudaLaunchAttributeProgrammaticStreamSerialization`) with `2 * num_sm` CTAs;
- the FA3 kernel executes `griddepcontrol.launch_dependents` at entry, so the FA2 grid starts as
  soon as FA3 is resident; the FA2 executor executes `griddepcontrol.wait` before exit, so the
  split-KV merge launched after it still follows the FA3 grid.

FA3 needs 164 KB of shared memory per CTA, so an FA2 CTA cannot share its SM: FA2 starts on the SMs
FA3 does not hold, and FA2 CTAs that are still unscheduled land on SMs FA3 CTAs vacate. That is the
cross-role backfill, done by the hardware block scheduler instead of by co-compilation. Excess FA2
CTAs find the queue empty and exit.

Readings:

2. **Where it lands depends on the FA2 class.** q4 verify rows (packed 28, tile 32) are at parity

**The A2 class-48 premise is refuted at 4 FA2 warps.** Tile 48 can only be laid out as 1 q-warp
x 4 kv-warps with `num_mma_q = 3`; its 3x per-warp O accumulator is what spills (648 B stack in
the executor alone), and it is slower than tile 64 at every q8 shape by 1.6-2.2x despite the
better fill (56/64 vs 56/48+16). The tail dispatcher (A2) is unaffected and stays on. Without a 32
class, q4 verify rows (packed 28) waste half of tile 64 (`mixed_verify` q4 0.095 vs 0.075), so
**64/32/16 is the set for q4/q8 MTP verify**; 128/64/16 only wins for 16-token rows (packed 112),
which the 4-mode schedule sends to FA3. With 64/32/16 the co-launched kernel beats
`BatchAttention` on the A2 mixed fixture (0.096 vs 0.106) and is 1.55x off the unfused two-launch
control there. The residual gap is largest on single rows and long KV, i.e. FA2 parallelism:
`FUSED_FA2_KV_CHUNK` sweep queued (`colaunch_chunk_20261012.sh`).

Small batches want short chunks (parallelism), large ones long chunks (per-item and merge cost).
**`FUSED_FA2_KV_CHUNK=auto`** (`fused_plan.cuh` `FusedAutoFa2KvChunk`): FA2 work =
sum over FA2 rows of kv_heads x q-tiles x kv; slots = `num_sm` without FA3 work, else
`2 x (num_sm - sm_split)`; chunk = smallest power of two >= max(256, work/slots). It picks the best
measured chunk or within 3% (mixed_verify q8) on every fixture above; host test
`FA2 auto KV chunk: PASS` pins it. Kernel gate of `auto` vs 1024 including shapes outside the fit
(kv 32768 single row, 32 rows at kv 8192, 32 verify rows beside a prefill chunk) is queued with
the serving A/B (`colaunch_serving_20261012.sh`).

**First `auto` build was WRONG on split rows (2026-10-12, `colaunch_serving_20261012.sh`):** every
pure-FA2 band shape where `auto` splits the KV failed all rows (e.g. kv4096 x 1 row, 8/8 bad),
while shapes where it picks a chunk >= kv (no split) passed. Cause: the planner's FA2
`len_kv_chunk` came from a second `FusedFa2KvChunk` call, which returns 0 ("no split") under
`auto`, so the runners took the direct-write path for rows whose partials the enumeration had
split -- the exact mismatch the planner comment warns about. The q4 serving-output gate with that
build failed too (long prefix 1). Its serving A/B was killed and is void. Fixed by passing the
override to both sites; v2 chain (`colaunch_serving_v2_20261012.sh`) re-runs the kernel gate and
stops before serving on any kernel- or output-gate failure.
