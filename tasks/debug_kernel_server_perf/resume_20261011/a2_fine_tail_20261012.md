# A2: per-work-item FA2 tail dispatch

This remains experimental (`FUSED_FA2_FINE_TAIL=1`, default off), not a closed
serving-performance item. The A/B task ordering in the main document is unchanged.

## Implementation and gates

`EnumerateFusedWorkItems` selects the smallest compiled FA2 class for the remaining
packed query extent. With classes 48/32/16 and GQA7, eight-token rows use 48+16
instead of 48+48. Both chunk-major and group-major plans retain the same query
coverage, split-KV partial count and merge destinations. FA3 routing is unchanged.

The first implementation exposed a class-handoff race: tile-48 has one query warp,
whereas tile-32 has two. Without a final work-item barrier, the extra query warp
can load the next class's Q into shared memory while the prior class still reads
its output scratch. The ragged FA2 null case passed with tail dispatch off and
failed with it on for seeds 2/3/4 (six bad rows of 30). A final
`persistent_block_sync` before shared-storage reuse clears all three failures.
Keep the pre-fence failures; they are not valid timing results for that corner.

- Host: 520 enumeration/merge cases, GQA4/7, query lengths 1–65, split/unsplit,
  chunk-major/group-major; existing host checks also pass.
- GPU after the fence: six ragged FA2 on/off seed arms and one FA3 split arm pass.
  Four mixed on/off/order arms, a ragged FA2 graph replay and an FA3 graph replay
  also pass. All use the existing causal fp32 reference and 2% head-error bound.
- Mixed fixture: 504 prefill tokens + eight eight-token verify rows, KV 2048,
  heads 28/4, SM split 112/132. Task counts change from `128/0/0/112` to
  `64/0/64/112`, retaining 896 partial rows; zero bad heads of 15,904 on replay.
- Graph timing, 50 iterations after 10 warmups: tail off/on is 0.5546/0.5096 ms
  (chunk-major) and 0.5574/0.5081 ms (group-major). These are bounded kernel
  measurements, not repeated serving gains. The fused arm is still roughly 4.8×
  slower than the valid `BatchAttention` control on this fixture.

## Serving boundary

**Superseded 2026-10-12:** the gate failures below were caused by the shared serving
stack, not the kernel. The YaRN override reset `rope_theta` 1e6 -> 1e4, so stock LPT itself was
wrong on 3/4 long prompts against an independent HF reference. After the fix the q8 gate passes
and TAIL1 is bit-identical to TAIL0 on all 12 requests; see
[a2_serving_ropefix_20261012.md](../resume_20261012/a2_serving_ropefix_20261012.md).
The original text is kept as the record of what was measured.

Before the tail implementation, both class sets 64/32/16 and 48/32/16 completed
the ShareGPT correctness workload: 12 requests, 3,301+ fused calls, zero fallbacks
and tracebacks. Against a fresh LPT control, long-request common prefixes are
`16,2,0,26`: **the serving-output gate fails**. The two fused class sets agree on
all 96 output tokens of each long request, but not all short-request outputs.
Four-token/GQA7 verification uses tile32 in both sets; this is not evidence of a
tile48-specific serving benefit, nor validation of the new tail path in serving.

The temporary stricter numerical diagnostic and proposed stock-relative margin
were reverted locally and remotely. The class-set runs exercised zero fp32
adjudications, so that unexecuted margin cannot explain their attention passes.
No acceptance criterion is relaxed to close the token mismatch.
