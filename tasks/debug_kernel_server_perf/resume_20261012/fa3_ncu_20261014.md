# FA3 bottleneck profiling

The SM-budget sweep did not recover the gap, and initial one-warp timings are
approximately unchanged. `fa3_ncu_20261014.sh` therefore profiles the implemented
FA3 kernels rather than choosing another configuration from speculation.

PID 613169 waits for the completed one-warp matrix and takes the existing GPU
lock. The installed profiler is Nsight Compute 2025.4.0. Four runs select the
dedicated gather primary, 128-thread TMA primary, 32-thread/232-register TMA
primary, and the stock `PrefillWithKVCacheKernel`. All use the same FA3-only
8x1024-query, KV32K fixture, page128 and SM budget112.

FA2 requests are absent, so kernel replay does not serialize an otherwise
required concurrent FA2 dependent. This is a diagnostic isolation of FA3, not a
serving benchmark or PDL-overlap measurement. Kernel replay and range replay
have different concurrency behavior; see the
[NVIDIA profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#replay).

The profiler collects launch, occupancy, throughput, scheduler, warp-stall,
memory, compute and instruction sections for one selected kernel per run.
Clock control is disabled; these profile durations must not replace the normal
timing-matrix results. Each application still runs its numerical checks. Reports
and exported CSVs stay under `/dev/shm/w/fa3_ncu_20261014` until collected.
Counter availability and results remain unproven until the run completes.

## V1 workload mismatch

V1 completed and obtained reports, but its application output revealed two
default FA2 requests despite the shell exporting an empty `FA2_REQUESTS`.
It therefore did not establish the intended FA3-only workload. Do not use it as
the isolated comparison described above. V2 uses the nonempty delimiter `,`,
which the harness parses as an empty request list, and asserts the application's
printed fixture before accepting each profile. No kernel is changed for this
input correction; the V1 reports remain separate.

## Verified V2 profiles

V2 completed at 00:56:33 +08:00 on 2026-10-14. Every application prints exactly
eight 1024-query/KV32768 FA3 requests and zero FA2 requests, and passes its output
checks. Each CSV contains one correctly named profiled kernel. Full exported
metrics, application logs, completion markers and remote report hashes are in
`fa3_ncu_v2_complete_20261014.json`.

| Profile | L2 hit rate | Tensor active (% peak elapsed) | Eligible warps/cycle |
|---|---:|---:|---:|
| Gather primary | 11.92% | 43.27% | 1.073 |
| TMA 128 producers | 96.11% | 40.75% | 0.570 |
| TMA 32 producers / 232 consumer registers | 96.14% | 40.88% | 0.531 |
| Stock FA3 | 77.60% | 65.29% | 0.971 |

All four have approximately 18.75% achieved occupancy and no reported local
spilling requests for this fixture. Thus the larger compiled stack frame is not
by itself evidence of an executed spill bottleneck here. TMA's improved cache
metrics also do not translate into stock-like tensor utilization.

The actual stock kernel uses `AttentionKernelTraits<0,128,128,128,96,2,...>`:
KV tile 96 and two stages, versus tile128/two stages in the custom kernels.
Stock also launches 132 CTAs versus the custom budget of112. Those differences
must not be attributed to one cause without controlled tests. The gather/TMA
comparison additionally changes work assignment, so the low gather hit rate
motivates testing the paired/round-robin assignment without TMA.

`fa3_locality_20261014.sh` starts that controlled A/B as PID 616642: same gather
binary, same 112-CTA budget, no hardware cluster, only the planner distribution
changes. Four fixtures and two reversed-order repeats retain all seven output
checks. The stock KV96 geometry requires a separate split-alignment experiment;
it is not enabled merely from this profile.
